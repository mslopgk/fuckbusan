## 1. 배경 (왜 이렇게 됐나)

- 진단 결과/상세 화면의 6각형 축 = **접근성 / 이동성 / 안전성 / 정보제공성 / 포용성 / 심미성**.
- 이 6축의 실데이터는 **과거 CSV/수집 데이터**에만 있음 (`checklist_result.질문기준` 컬럼에 축 이름이 태그된 1,607건, 최종 2026-05-28).
- **현재 사용자 진단폼**(PC/모바일)은 중분류별 만족도 문항 **4개**만 받고 `질문기준`을 저장하지 않음 → 신규 제출(6,003건)은 6축에 반영 불가.
- 6축을 서버 집계(`/checklist/criteria-summary`)로 뽑으면 **전역 평균(1.90) 고정** → 어느 진단을 눌러도 똑같이 떠서 "고장난 것 같다"는 지적 발생.

## 2. 임시 구현 내용 (억지 매핑)

각 진단의 **만족도 답변(`answers`, 1~5)** 으로 그 진단의 6각형을 직접 산출:

```
answers 예: {"0":3, "1":4, "2":3, "3":3}   (문항 4개)

→ 문항 순서대로 앞 축부터 채움:
   접근성=3, 이동성=4, 안전성=3, 정보제공성=3
→ 남는 축(포용성, 심미성) = 답변 평균(3.25)로 채움
```

- 답변이 6개면 6축 그대로, 4개면 4축+2축(평균), 답변 없으면 "데이터 준비중".
- **핀(진단)마다 자기 답변으로 다른 6각형** → per-pin 실데이터로 동작.

## 3. ⚠️ 한계 (억지의 대가 — 대표님 확인 필요)

1. **축 라벨이 문항 의미와 정확히 안 맞음.** 문항 순서(위치)로 축에 꽂기 때문. 예: 1번 문항이 "장애물이 보행을 방해하지 않나요?"인데 축은 "접근성"으로 표시됨. 게다가 중분류마다 문항 내용이 달라 라벨-내용 대응이 일정하지 않음.
2. **2개 축(포용성·심미성)은 실제로 물어본 값이 아니라 나머지 답변의 평균**으로 채운 값.
3. 즉 **숫자·모양은 사용자 실답변에서 나오지만, 6축 라벨의 의미는 부정확한 "보여주기용"** 6각형.

## 5. 정식 해결책 (내일 결정용)

**진단폼의 만족도 문항을 6개 평가기준(접근성~심미성)으로 재설계**하는 것이 정석:
- 사용자가 6축을 직접 평가 → 답변이 곧 정확한 6각형 (라벨=의미 일치).
- 신규 제출부터 정확한 per-pin 데이터 축적.
- 단 현재 "중분류별 내용 문항"을 "6축 문항"으로 교체해야 함 → **문항 스펙(협력사) 확정 필요**.

→ 내일 대표님께 (A) 이 임시안 유지 / (B) 6축 문항으로 정식 재설계 중 확인받고 진행.
